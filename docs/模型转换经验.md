# MMD 模型转《影之刃零》主角替换的经验

本次使用 LeMalin 的 PMX 模型，经 Blender 导出游戏变形骨架，在 UE 5.7 中生成运行时重定向、物理、材质及面板。下面按问题整理，重点保留已找到原因、已修复或有实机对照的处理方法。

## 1. 静止正常，运动时像纸模被压扁

### 当时看到的现象

角色站着基本正常，动作开始后身体先压缩再展开，脸与头发像分离的整块，拿武器的手掌尤其扁。由于输入是 MMD 模型，最初考虑过特殊蒙皮、扭转与骨骼缩放。

最终原因出在顶点组筛选。MMD Tools 导入后除了骨骼组，还带有 `mmd_edge_scale`、`mmd_vertex_order` 等数据组。早期转换对每个顶点组调用骨骼回退映射，找不到对应骨骼时回到 root。这样把辅助数据当作蒙皮权重，合并进 root 后又一起归一化。

某顶点原本的真实骨骼权重总和为 1。如果又加入接近 1 的辅助组值，归一化后真实骨骼只剩大约一半影响，另一半跟着 root。角色动作越大，混入的静止 root 与真实骨骼变换差异越明显。

### 修正的核心

```python
source_bone_names = set(old.data.bones.keys())
groupmap = {
    group.index: resolve(group.name)
    for group in mesh.vertex_groups
    if group.name in source_bone_names
}

for vertex in mesh.data.vertices:
    weights = {}
    for influence in vertex.groups:
        if influence.group not in groupmap:
            continue
        bone = groupmap[influence.group]
        weights[bone] = weights.get(bone, 0) + influence.weight
    assert sum(weights.values()) > 0
    # 只对这份真实骨骼权重归一化，再写入新骨架。
```

判断依据应来自实际源 Armature 骨名。只排除这次遇到的两个组名，仍可能遗漏其他模型的辅助数据组。

### 修复如何确认

源模型有 153,033 个顶点，错误转换让全部顶点带上 root 权重，源侧错误 root 权重范围约为 0.50–0.67。修正后源侧 root 权重顶点数为 0，所有真实权重完成归一化。实际烹饪导出网格中的 root 权重也从遍布全部顶点变为 0，用户实机确认动作压缩和脸发分离消失。

烹饪导出的顶点数会受 UV、材质和法线拆点影响，不能强求与 PMX 完全相同。这里核对的是蒙皮分布，实际拆点数量差异需要结合导出方式判断。

本模型使用 BDEF1/BDEF2/BDEF4，没有 SDEF。这次结论只能证明上述非骨骼数据污染问题，带 SDEF/QDEF 或复杂附加变形的模型还需要单独处理。[转换实现](../tools/prepare_game_model.py)、[源权重修复记录](evidence/weight-fix.json)、[错误包蒙皮统计](evidence/cooked-weights-before.json)、[修复后蒙皮统计](evidence/cooked-weights-fixed.json)

## 2. MMD 控制骨与游戏变形骨架的对应

MMD 骨架包含操作控制、D 骨、扭转、IK、附加变形和各种饰物链。转换时要分别回答三个问题。

1. 顶点真正由哪些骨影响。
2. 这些骨在新骨架中对应谁，是否需要合并权重。
3. 各骨的参考位置、朝向与父子关系是否仍能解释原有蒙皮。

本次建立了人体映射和权重别名。脚部 D 骨映射到腿和脚，手臂扭转组按当前方案合并到上臂或前臂，头发、兔耳等加权辅助链连同必要父骨一起保留。辅助骨改成 `aux_***` 名称，原名对应关系写进生成报告。

导出前把脚底抬到地面，统一到厘米制作空间。FBX 导入还可能多出包装根，所以运行时骨数应结合实际导入结果核对。原 PMX 的原始骨骼与控制结构留在最初导入的 Blender 工程中。

UE 侧建立人体链映射，使用源角色动画和 `RetargetPoseFromMesh` 驱动新角色。原角色显示组件与新模型显示组件的骨架、参考比例及组件缩放要分别看，最终 125% 外观缩放也会影响武器握点观感。

手臂长度、参考姿态与握点之间存在关联。本次接受了现有手臂比例和少量握持偏差。新模型若要精确握刀，应先定义真正的掌心接触点，再核对源手骨、目标手骨和最终显示缩放。单看 hand 骨位置误差不足以判断刀柄是否贴合掌心。[骨架转换](../tools/prepare_game_model.py)、[重定向资产生成](../tools/ue_build_prototype.py)

## 3. 辫子为什么始终像一整块

早期方案用运动输入驱动骨骼角度弹簧，先让整体头发摆动，再给各段增加延迟。即使加大幅度，长辫子仍缺少重量感。用户观察到蝴蝶结上方明显移动，下方长辫子却像一整块。

调查先确认了辫子的骨段及权重存在。问题主要来自求解方式与驱动范围。角度弹簧会围绕参考角度回弹，缺少长链在重力下悬垂、随锚点移动再摆荡的行为。继续加大同一输入会强化整体甩动。

后续改用 UE 原生 RigidBody，建立两侧独立刚体链。最终每侧 A0 为运动学锚点，A1–A6 为动态段，世界重力为 `(0, 0, -980)` cm/s²。源 PMX 形状、骨位置和质量用于构造制作侧输入，再转换到目标网格参考空间。

关节框架按实际骨链方向建立，分别转换到父体和子体局部空间。仅凭骨骼名字复制欧拉角限制，容易把本来想控制的前后摆动施加到另一个轴。

这次用户明确认可改为重力链后的自然程度。随后收回早期为放大差异而增加的响应，并关闭额外急转驱动，让运动主要经实际锚点和原生求解传入。

换模型时，先确定锚点和各动态段覆盖的网格区域，再调质量、阻尼、恢复力和角限。一次改变一类因素，按正常视距观察启停、掉头和前倾。[PMX 骨链调查](../tools/investigate_hair.py)、[辫子物理生成](../project/ProjectPBZ/Source/HcxEditor/LeMalinBraidPhysics.inl)、[动画图接入](../project/ProjectPBZ/Source/HcxEditor/LeMalinLiveliness.inl)

## 4. 改了关节参数，保存后却没有保留下来

创建 `UPhysicsConstraintTemplate` 时，修改 `DefaultInstance` 还需要提交序列化所用的默认配置。否则编辑时读到的值与重新加载或烹饪后的值可能不同。

本次使用以下顺序。

```cpp
auto& Constraint = Template->DefaultInstance;
Constraint.SetAngularDriveMode(EAngularDriveMode::SLERP);
Constraint.SetOrientationDriveSLERP(true);
Constraint.SetAngularDriveParams(10.f, 2.f, 0.f);
Template->SetDefaultProfile(Constraint);
```

定位这类问题时，检查保存并重新加载后的资产，或实际包解析出的配置。函数调用成功只能说明当时操作了某个对象，持久化值还需要对应证据。[关节生成实现](../project/ProjectPBZ/Source/HcxEditor/LeMalinBraidPhysics.inl)

## 5. 头发与身体、左右兔耳的碰撞

辫子有重力后，穿过身体的问题更明显。本次从 PMX 身体刚体形状整理出 14 个简化形状，附着到 11 个身体骨骼。身体保持运动学，碰撞体随动作走，辫子动态体与这些部位接触。

碰撞过滤只开启所需的辫子—身体接触。身体之间、锚点之间以及辫子自碰撞保持关闭。接触材质使用低摩擦、零反弹，减少卡肩和挂住的观感。碰撞体的大小需要兼顾外观缩放、姿势变化和头发实际厚度。

兔耳另建从根到尖的两条动态链，以角限和恢复力形成软耳与竖耳。左右耳形状来自实际蒙皮几何，启用耳间碰撞后解决两耳交叉穿插。用户最终保留两种模式作为可选项。

这套方法适合当前饰物结构。裙摆、长飘带或不同厚度的头发，需要重新选择形状与过滤关系，当前参数没有直接通用性。[身体形状配置](../metadata/body-colliders.json)、[耳部物理生成](../project/ProjectPBZ/Source/HcxEditor/LeMalinEarPhysics.inl)

## 6. 日光下发白，调高光与亮度却没有变化

同一角色在阴影中正常，在日照下明显发白。早期材质参数能够写入 MID，但用户实机看不到效果。参数存在、写入成功、游戏最终着色发生变化，分别需要不同证据。

本次用几种单项对照缩小范围。

| 对照 | 用户观察 | 能支持的判断 |
| --- | --- | --- |
| 原样与关闭高光 | 几乎无差别 | 这条调整路径对当前现象帮助有限 |
| 线性底色减半 | 略有改善 | 实际底色资源对受光结果有影响 |
| 黑底色定位 | 明显变黑 | 材质与颜色切换确实生效 |

最终采用底色 2 档作为可接受方案。白色基础纹理这一档对应线性反射率 25%，黑色风格后来使用了单独调整的倍率。它会连带改变阴影观感，因此用户在日光与阴影中共同比较后才定下默认值。

底色应在线性空间做倍率，再编码回 sRGB。原始 alpha、图像尺寸和非目标部位保持一致，方便比较颜色本身的影响。Normal 和 Mix 需要依据真实父材质的层参数及通道绑定，不能仅凭通用 ARM 命名套用。

本次复用游戏已编译父材质和着色器，创建本模组材质实例。游戏本身的材质参考桩、字体和 UI 贴图留在制作工程，按白名单排除，运行时引用客户端已有路径。[底色生成](../tools/prepare_sun_comparison.py)、[材质实例绑定](../tools/ue_prepare_game.py)、[底色材质导入](../tools/ue_prepare_sun_comparison.py)

## 7. 黑色风格、丝袜连续性和常用视距

把整张图染黑，容易同时染掉扣件，也会留下与服饰同图但未识别的白色布带。本次根据材质槽和 UV 连通岛区分布料、饰件、鞋与金属，布带统一深色，扣件保留银白。黑色风格拥有独立底色与表面数据，白色仍引用原有方案。

丝袜早期只识别两条长腿的连通组件，漏掉胯部和大腿上段，导致下半身出现四角裤式分界。模型拓扑的连通边界和服装设计边界并不总一致。后来合并四个相关组件，才让下半身呈连续丝袜效果。

随后用镜亮、全哑、平滑法线和强波纹逐项对照。夸张波纹在游戏中明显可见，确认法线有效，但普通细织纹在正常视距收益很小。用户最终选择全哑，再配合连续的肤色与厚度变化，减轻均匀塑料筒感。

当前薄透感来自不透明底色模拟，结合腿部高度、朝向与侧向厚度生成变化。它有当前风格的视觉效果，同时保留这一实现前提。更细的纹理应先按正常游戏距离判断收益，再决定投入。[黑色分区](../tools/prepare_black_style.py)、[连续丝袜处理](../tools/prepare_sheer_stockings.py)

眼睛也经历了类似取舍。单独提高表面光泽，近看有所不同，常用距离变化较小。后续突出原有白色星形瞳孔、集中主高光并强化虹膜青蓝层次，用户更容易感知。最终一般/宝石作为两个选项保留。

## 8. 自动眨眼、表情和眼神怎样协作

从原 PMX 选择少量顶点 morph，组合成慵懒、微笑、认真三组。眼皮与嘴眉分开烘焙，运行时用平滑插值混合。眨眼接近闭合时，眼皮表情按 `1 - BlinkProgress` 让位，减少叠加挤压。

自动表情每 4–8 秒选择一次原样、慵懒或微笑。随机结果先存进状态，再用于后续过渡，避免蓝图纯随机节点在不同使用处重新取值。

眼骨在简化人体骨架中已经并入头部，所以制作侧读取原眼骨权重和目戻 `-.7` 补偿关系，将左右 4°、上下 2°的小角度变换烘焙成四个 morph。运行时每 2–5 秒调整目标，移动时回正，闭眼时降低视线形变。

这保留了现有头部蒙皮与动画骨架，当前小幅眼神已获实机认可。更大角度、不同眼球形状或目标锁定需要重新评估形变和眼睑关系。[morph 生成](../tools/prepare_lively_model.py)、[眼神控制](../project/ProjectPBZ/Source/HcxEditor/LeMalinGaze.inl)

## 9. 工具小刀为什么后移正常，却一直漏隐藏

偏移与隐藏走的是不同处理路径。工具小刀会跟背挂后移，只能证明偏移路径找到了它，不能证明显隐遍历也覆盖到了它。

实机挂接记录确认，Knife 与 KnifeScab 直接挂在源角色的 CharacterMesh0，真实插槽名带有 `_Socket` 后缀，刀本体是可渲染的根组件。

问题来自蓝图纯节点的输出临时数组。早期先对 `GetChildrenComponents` 的结果追加 Root，再读取长度并遍历。后续读取触发纯节点重新求值，得到原来的后代数组，先前追加的 Root 没有被保留。于是刀的子网格被处理，真正刀本体仍然显示。

修正顺序如下。

```text
GetChildrenComponents
  → 将输出赋给成员数组 BackHideParts
  → BackHideParts.Add(Root)
  → 遍历 BackHideParts
```

测试对象也需要包含可渲染根组件，以及没有子网格的刀鞘。只用不可渲染的空根加子网格，容易错过这个问题。修复后用户确认小刀一起隐藏。

偏移与显隐的状态恢复也需要明确归属。记录本模组修改过的原位置、最后应用位置与隐藏状态，在拔刀、重挂接、开启显示时恢复对应修改，避免把游戏自身隐藏的组件强行显示出来。[背挂实现](../project/ProjectPBZ/Source/HcxEditor/LeMalinBackMount.inl)、[制作期挂接记录入口](../project/ProjectPBZ/Source/HcxEditor/LeMalinBackDiagnostics.inl)

## 10. 实时面板与玩家面板

早期参数不稳定时，将模型大小、阻尼、重力、材质档位和预览方向放进实时面板，能显著缩短反复退出、重打包的时间。功能定稿后，玩家分支收敛为服饰、兔耳、眼睛、背挂显隐、后移距离、自动表情和眼神七项。

开关用勾选，风格用具名选项。玩家与开发保存槽分开，避免历史开发值带入玩家默认表现。UI 调查使用游戏原有字体、箭头、纸纹、边框资源，编辑器用同路径资源预览，玩家包运行时解析游戏自带资源。

验证也按问题选择。第一次权重错误需要源侧和实际包双向核对，材质问题需要同场景单项对照，数值上限小改则直接构建部署交给实机。每次检查都应能回答当前具体问题，记录对应范围，省下来的时间用于真正能看到变化的调整。[玩家面板](../project/ProjectPBZ/Source/HcxEditor/LeMalinPlayerPanel.inl)、[原生视觉引用](../project/ProjectPBZ/Source/HcxEditor/LeMalinNativeUi.inl)
